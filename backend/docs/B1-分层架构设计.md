# 分层架构设计 - 为什么要分层？

## 核心问题
代码混乱、难以维护的根源是什么？

## 不分层的问题

### 1. 业务逻辑散落各处
```javascript
// routes/chat.js - 糟糕的例子
router.post('/chat', async (req, res) => {
  const { message } = req.body;

  // HTTP 处理
  if (!message) {
    return res.status(400).json({ error: '消息不能为空' });
  }

  // 业务逻辑（不应该在这里）
  const aiResponse = await callAI(message);

  // 更多业务逻辑（越来越乱）
  await saveToHistory(message, aiResponse);

  // 工具调用（更不应该）
  if (message.includes('天气')) {
    const weather = await fetchWeather();
    // ...
  }

  res.json({ response: aiResponse });
});
```

### 2. 改一处影响全身
- 修改 AI 提供商可能影响所有路由
- 添加新功能需要理解整个代码库
- 新人上手困难

### 3. 无法单独测试
- 测试需要启动整个服务器
- 无法模拟 HTTP 请求和业务逻辑

## 六层架构解决方案

```
┌─────────────────────────────────────────────────────────┐
│                      routes/                            │  HTTP 处理
│                  参数校验、响应格式                        │
├─────────────────────────────────────────────────────────┤
│                     services/                           │  业务流程
│               聊天编排、Agent 执行                         │
├─────────────────────────────────────────────────────────┤
│                      domain/                            │  核心业务
│            意图分类、工具选择、检索排序                      │
├─────────────────────────────────────────────────────────┤
│                       infra/                            │  基础设施
│              熔断、限流、缓存、指标采集                      │
├─────────────────────────────────────────────────────────┤
│                      common/                            │  通用基础
│                  错误定义、日志规范                         │
├─────────────────────────────────────────────────────────┤
│                   application/                         │  应用编排
│                  跨模块协调、编排                          │
└─────────────────────────────────────────────────────────┘
```

## 各层职责详解

### 1. routes/ - HTTP 处理层
**职责**：接收请求、参数校验、调用下层、格式化响应

```javascript
// routes/chat.js
router.post('/chat', async (req, res) => {
  // 1. 参数校验
  const { message } = req.body;
  if (!message) {
    return res.status(400).json({ error: '消息不能为空' });
  }

  // 2. 调用 services
  const result = await chatService.sendMessage(message);

  // 3. 格式化响应
  res.json({ response: result });
});
```

### 2. services/ - 业务逻辑层
**职责**：业务流程编排、事务管理

```javascript
// services/chatService.js
class ChatService {
  async sendMessage(message) {
    // 1. 意图识别
    const intent = await intentClassifier.classify(message);

    // 2. 路由决策
    if (intent === 'tool') {
      return await this.handleTool(message);
    } else if (intent === 'rag') {
      return await this.handleRAG(message);
    }

    // 3. AI 生成
    return await this.callAI(message);
  }
}
```

### 3. domain/ - 核心业务层
**职责**：纯业务逻辑、不依赖框架

```javascript
// domain/rag/QueryRewriteService.js
class QueryRewriteService {
  // 问题重写：补全上下文
  rewrite(query, context) {
    // 纯业务逻辑，无副作用
    return this.addContext(query, context);
  }

  // 问题拆分：复杂问题拆子问题
  decompose(complexQuery) {
    // 纯业务逻辑
    return this.splitIntoSubQueries(complexQuery);
  }
}
```

### 4. infra/ - 基础设施层
**职责**：技术基础设施、可复用组件

```javascript
// infra/circuitBreaker/CircuitBreaker.js
class CircuitBreaker {
  async execute(fn) {
    if (this.state === 'OPEN') {
      throw new CircuitOpenError();
    }

    try {
      const result = await fn();
      this.recordSuccess();
      return result;
    } catch (error) {
      this.recordFailure();
      throw error;
    }
  }
}
```

### 5. common/ - 通用基础层
**职责**：错误定义、日志规范、通用工具

```javascript
// common/errors/AppError.js
class AppError extends Error {
  constructor(code, message, statusCode = 500) {
    super(message);
    this.code = code;      // 业务错误码
    this.statusCode = statusCode;
  }
}

// 错误分类
class ValidationError extends AppError {
  constructor(message) {
    super('VALIDATION_ERROR', message, 400);
  }
}

class UnauthorizedError extends AppError {
  constructor(message = '未授权') {
    super('UNAUTHORIZED', message, 401);
  }
}
```

### 6. application/ - 应用编排层
**职责**：跨模块协调、复杂流程编排

```javascript
// application/ChatOrchestrator.js
class ChatOrchestrator {
  async process(message, sessionId) {
    // 1. 加载会话记忆
    const memory = await this.memoryService.load(sessionId);

    // 2. 意图识别 + RAG 检索
    const [intent, context] = await Promise.all([
      this.intentClassifier.classify(message),
      this.ragService.retrieve(message)
    ]);

    // 3. Agent 执行
    const response = await this.agentEngine.run({
      message,
      intent,
      context,
      memory
    });

    // 4. 保存记忆
    await this.memoryService.save(sessionId, message, response);

    return response;
  }
}
```

## 分层的好处

| 好处 | 说明 |
|------|------|
| 关注点分离 | 每层只关心自己的职责 |
| 易于测试 | 可以单独测试每层 |
| 可复用 | infra 和 common 可跨项目复用 |
| 并行开发 | 不同层可以分配给不同人 |
| 易于维护 | 修改某层不影响其他层 |

## 新手常见问题

Q: 什么时候放 routes？什么时候放 services？
A: 路由只做 HTTP 相关的事（参数校验、响应格式），业务逻辑放 services

Q: domain 和 services 有什么区别？
A: domain 是纯业务逻辑（无依赖），services 调用 domain 实现业务流程

Q: 如何避免循环依赖？
A: 上层调用下层，下层不调用上层。application → services → domain → infra

Q: 小项目也需要分层吗？
A: 建议至少分成 routes/services 两层，避免业务逻辑散落
