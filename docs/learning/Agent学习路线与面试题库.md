## 一、后端转 Agent 知识映射

### 1.1 后端技能 → Agent 技能对照

| 后端技能 | Agent 对应 | 说明 |
|----------|-----------|------|
| API 设计/HTTP | Function Calling | LLM 调用外部工具 |
| 异步/线程池 | ReAct 循环 | Agent 执行循环 |
| 重试/降级/限流 | 熔断/重试机制 | Agent 容错处理 |
| MySQL/Redis | 向量库/记忆存储 | Agent 记忆系统 |
| SpringBoot | LangChain/LangGraph | Agent 开发框架 |
| 缓存策略 | RAG 检索缓存 | 减少重复计算 |

### 1.2 后端视角理解 Agent

```
传统后端架构：
用户请求 → Controller → Service → DAO → Database
                              ↓
                      业务逻辑处理

Agent 架构：
用户请求 → Intent识别 → 规划(Plan) → 执行(Act) → 观察(Observe) → 循环
                              ↓
                      工具调用 = 后端 API
                      记忆 = 数据库
                      RAG = 搜索引擎
```

#### 3. ReAct 核心范式

```javascript
// ReAct 执行循环
async function ReActLoop(userQuery, tools, llm) {
  const history = [{ role: 'user', content: userQuery }];

  while (true) {
    // Step 1: Reason - LLM 分析当前状态，决定下一步
    const response = await llm.chat([
      ...history,
      { role: 'user', content: '请决定下一步行动' }
    ]);

    // Step 2: Act - 执行工具或返回结果
    if (response.tool_calls) {
      for (const tool of response.tool_calls) {
        const result = await executeTool(tool.name, tool.arguments);

        // Step 3: Observe - 添加结果到历史
        history.push({
          role: 'tool',
          name: tool.name,
          content: JSON.stringify(result)
        });
      }
    } else {
      // 没有工具调用，返回最终结果
      return response.content;
    }
  }
}
```

const workflow = new StateGraph({
  messages: []
});

// 定义节点
workflow.addNode('input', (state) => ({ messages: [...state.messages, 'input'] }));
workflow.addNode('analyze', (state) => ({ messages: [...state.messages, 'analyzed'] }));

#### 3. RAG 面试高频问题

```
Q: 为什么要切片？不切片有什么后果？

A:
1. 向量化失真：长文档语义复杂，压缩到单一向量丢失细节
2. 检索精度下降：相关片段被无关内容稀释
3. 上下文超限：超出 LLM 上下文限制
4. 粒度不细：用户只需要某一段，返回整篇增加噪声
```

```
Q: chunk_size 和 overlap 怎么设置？

A:
chunk_size:
- 短文本(100-300): 精确匹配场景
- 中等(300-500): 通用场景，推荐
- 长文本(500-1000): 需要上下文完整性

overlap:
- 叙事性文档: 10-20%
- 技术文档: 20-30%（上下文关联强）
- 对话: 30-50%

原则: 防止语义截断，但也不能太大导致噪声
```

```
Q: 混合检索中 BM25 和向量的权重怎么定？

A:
两种方式:
1. RRF (Reciprocal Rank Fusion):
   RRF = 1/(60 + rank_vector) + 1/(60 + rank_bm25)
   更鲁棒，不依赖具体分数

2. 固定比例:
   score = 0.7 * vector_score + 0.3 * bm25_score
   需要根据效果调整比例

我们测试 RRF 召回率提升 12%
```

│  - 分片索引: 按业务/部门划分                                        │
│  - 缓存: Redis 缓存高频查询结果                                      │
│  - 量化: INT8/FP16 减少向量大小                                      │
│  - 异步: 预加载热点数据                                              │
│                                                                      │
│  Q2: 文档频繁更新，向量库如何保证一致性？                           │
│  A:                                                                    │
│  - 增量更新: 只更新变化的文档                                        │
│  - 版本管理: 每个文档带版本号                                        │
│  - 软删除: 标记删除，不立即物理删除                                  │
│  - 定时合并: 定期清理过期数据                                        │
│                                                                      │
│  Q3: 表格、PDF 图片的 RAG 如何处理？                                │
│  A:                                                                    │
│  - 表格: 转为 Markdown 表格，保留行列关系                             │
│  - PDF 图片: OCR 提取文本                                             │
│  - 布局保留: 使用多模态模型（如 GPT-4V）                            │
│                                                                      │
│  Q4: 长文档"中间内容丢失"问题如何解决？                             │
│  A:                                                                    │
│  - 父子分块: 大块存父子关系，小块检索                                 │
│  - 分层检索: 先召回父块，再召回子块                                    │
│  - 重排序: 父子块一起重排                                            │
│                                                                      │
│  Q5: RAG vs Fine-tuning 如何选型？                                  │
│  A:                                                                    │
│  - RAG: 知识更新频繁、需要可解释性、成本低                           │
│  - Fine-tuning: 任务固定、数据量大、延迟敏感                          │
│  - 现实: 两者结合，RAG 做知识库，Fine-tuning 优化特定任务              │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 模块四：LLM 工程化

┌─────────────────────────────────────────────────────────────────────┐
│                    LLM 工程化面试题                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  Q1: 峰值 QPS 100+ 如何做排队和削峰？                               │
│  A:                                                                    │
│  - 令牌桶限流: 控制并发数                                            │
│  - 队列缓冲: 请求入队，按优先级调度                                   │
│  - 批量推理: 合并多个相似请求                                         │
│  - vLLM/TGI: 服务端优化                                              │
│                                                                      │
│  Q2: vLLM PagedAttention 的原理？                                    │
│  A:                                                                    │
│  - 传统 KV Cache: 一次性分配大内存，碎片化                          │
│  - PagedAttention: 虚拟显存分页，按需分配                            │
│  - 利用率提升 2-4 倍                                                 │
│                                                                      │
│  Q3: 模型量化（INT8/INT4）的原理与坑？                              │
│  A:                                                                    │
│  - 原理: 降低权重精度，减少内存和计算                                 │
│  - 坑: 精度损失、某些任务效果下降                                     │
│  - 建议: INT8 优先，延迟敏感用 INT4                                   │
│                                                                      │
│  Q4: 如何防止恶意用户刷 Token？                                       │
│  A:                                                                    │
│  - 输入长度限制: max_tokens                                           │
│  - 频率限制: 单用户 QPS 限制                                          │
│  - 成本监控: 超过阈值告警                                             │
│                                                                      │
│  Q5: 如何设计多模型调度？                                            │
│  A:                                                                    │
│  - 小模型: 简单任务（如意图识别）                                     │
│  - 大模型: 复杂推理                                                  │
│  - 调度策略: 规则/代价模型/强化学习                                  │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```
