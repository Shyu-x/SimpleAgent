#### 面试官

```
面试官：好，我注意到你用到了 RRF 融合。RRF 的公式是什么？为什么不用简单的分数加权？
```

#### 面试者

```
RRF 的公式是：

RRF(d) = Σ 1/(k + rank_i(d))

其中：
- d 是文档
- k 是常数（通常取 60）
- rank_i(d) 是第 i 个检索通道中文档 d 的排名

具体到两种检索融合：
RRF_score = 1/(60 + vector_rank) + 1/(60 + bm25_rank)

不用简单加权的原因有三个：

1. **分数不可比**：向量相似度是 [0,1]，BM25 是 IDF 权重，量纲不同
2. **排名更鲁棒**：RRF 只依赖排名，不依赖具体分数，对异常值不敏感
3. **融合效果稳定**：实验表明 RRF 在各种查询类型下表现一致

我们测试过两种方式，RRF 的召回率比固定加权提升了 12%。
```

---

#### 面试官

```
面试官：追问一下，RRF 中这个 k=60 是怎么确定的？有调过这个参数吗？
```

#### 面试者

```
这个 k 值的选择确实有讲究：

k 的作用是调节排名差异的重要性：
- k 越小，排名靠前的文档优势越明显
- k 越大，不同排名之间的差异越小

常见的经验值：
- k=60：通用场景，效果稳定
- k=30：排名差异更敏感
- k=100：更平滑

我们确实调过，用 grid search：
- 测试了 k = 20, 30, 40, 50, 60, 80, 100
- 评估指标：MRR@10 + Recall@5
- 结果：k=60 时 MRR 最高，k=80 时 Recall 最高
- 最后选了 k=60，因为我们的场景对 precision 要求更高

但说实话，这个参数的影响没有那么大，10% 以内的波动。
```

---

#### 面试官

```
面试官：好，你说最终返回 5 个 chunk。为什么是 5 个？有没有针对这个数量做过验证？
```

#### 面试者

```
这个数量确实是我们做过验证的。

我们的选择逻辑：

1. **先召回后截断**：初筛 20 个，经过 Rerank 后取 top 5

2. **验证方法**：
   - 计算每个 chunk 的 token 数
   - 5 个 chunk 平均 1500 tokens，加上问题和其他 Prompt，总共约 2000 tokens
   - LLM 上下文限制是 8K，完全够用

3. **A/B 测试结果**：
   - 返回 3 个：Recall@5 = 0.72
   - 返回 5 个：Recall@5 = 0.89  ← 最终选择
   - 返回 10 个：Recall@5 = 0.91，但 cost 增加了 80%

所以在效果和成本之间取了平衡，选择了 5 个。
```

---

#### 面试官

```
面试官：如果我想把召回率再提升，你有什么优化思路？
```

#### 面试者

```
可以从这几个方向优化：

1. **Query 层面**：
   - HyDE：用 LLM 先生成假设答案，再检索
   - Query Expansion：把一个问题展开成多个子问题
   - 加入用户历史查询的上下文

2. **Retrieval 层面**：
   - 增加更多召回通道（如稀疏向量、KG 检索）
   - 调整 RRF 的 k 值
   - 使用 ColBERT 等更细粒度的向量模型

3. **Rerank 层面**：
   - 尝试更强大的 CrossEncoder 模型
   - 使用 LTR（Learning to Rank）模型

4. **数据层面**：
   - 优化文档切片策略（重叠比例、切片长度）
   - 增加数据增强

我们实际落地了 Query Expansion，效果提升 8%。
```

### 第二轮：Agent 记忆系统拷问

#### 面试官

```
面试官：你在项目中设计了长短期记忆，能详细讲讲这三层记忆分别存什么？什么时候触发记忆的压缩？
```

#### 面试者

```
我们设计了严格的三层记忆架构：

┌─────────────────────────────────────────────────────────────┐
│ Working Memory (~8K tokens)                                │
│ LLM 直接看到的上下文                                         │
│  - System Prompt (2K)                                       │
│  - 当前对话历史 (~4K)                                        │
│  - 从 Session Memory 提取的近期内容 (~2K)                    │
└─────────────────────────────────────────────────────────────┘
                            ↓ 提取
┌─────────────────────────────────────────────────────────────┐
│ Session Memory (~50K tokens)                                │
│ 当前会话的完整记忆                                            │
│  - 最近 50 轮对话原始内容                                    │
│  - 关键决策点摘要                                            │
│  - 未解决的问题队列                                          │
└─────────────────────────────────────────────────────────────┘
                            ↓ 压缩
┌─────────────────────────────────────────────────────────────┐
│ Persistent Memory (~无限制)                                  │
│ 跨会话的持久记忆                                             │
│  - Session Notes：每轮对话的摘要                              │
│  - 用户偏好：独立存储的 key-value                            │
│  - 知识库：RAG 检索结果                                       │
└─────────────────────────────────────────────────────────────┘
```

#### 压缩触发机制：

```
触发条件（满足任一）：
1. Session Memory Token 超过 50K
2. 对话轮次超过 50 轮
3. 用户明确说"换个话题"

压缩策略：
1. 保留：关键决策、用户偏好、未解决问题
2. 摘要：普通对话历史，用 LLM 生成摘要
3. 丢弃：过于细节的信息（如具体的试错过程）
```

#### 面试官

```
面试官：如果用户说"我不记得刚才聊到哪了"，你系统怎么处理？能实现续聊吗？
```

#### 面试者

```
这个场景我们专门处理过。

实现方式：

1. **Session Notes 机制**：
   - 每次对话结束时，自动生成 Session Note
   - 包含：话题是什么、结论是什么、还有什么没解决

     {
       topic: "用户咨询保险产品",

       pending: ["等待用户确认预算"],
       timestamp: "2024-01-15"
     }

2. **续聊流程**：
   用户说"继续"
       ↓
   查找上一个 Session Note
       ↓
   取出 pending 问题
       ↓
   构建上下文：pending + 简要摘要
       ↓
   LLM 继续对话

3. **实际效果**：
   - 用户感知：80% 能顺利续聊
   - 失败原因：跨 Session 的上下文丢失（约 20%）
```

```

#### 面试者

```
这是典型的 RAG 兜底场景：

┌─────────────────────────────────────────────────────────────┐
│                    Out-of-Knowledge Handling                  │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  判断流程：                                                  │
│                                                              │
│  用户问题                                                    │
│      ↓                                                       │
│  RAG 检索 (topK=5)                                          │
│      ↓                                                       │
│  ┌─────────────────┐                                         │
│  │ 检索结果质量检测 │                                        │
│  │                 │                                        │
│  │ avg_score > 0.8 │ → 高置信 → 正常回答                   │
│  │ avg_score > 0.5 │ → 中置信 → 回答 + 标注来源           │
│  │ avg_score < 0.5  │ → 低置信 → 拒答或转人工             │
│  └─────────────────┘                                         │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

#### 面试者

```
具体实现：

1. **置信度检测**：
   ```javascript
   function estimateConfidence(results) {
     if (results.length === 0) return 'low';
     const avgScore = results.reduce((s, r) => s + r.score, 0) / results.length;

     if (avgScore > 0.8) return 'high';
     if (avgScore > 0.5) return 'medium';
     return 'low';
   }
   ```

2. **不同置信度的响应**：
   ```javascript
   switch (confidence) {
     case 'high':
       return generateAnswer(results);  // 正常回答

     case 'medium':
       return generateAnswer(results) + '\n⚠️ 以上仅供参考';  // 提示不确定性

     case 'low':
       return '抱歉，我没有找到与您问题相关的准确信息。\n' +
              '建议您：\n' +
              '1. 换个方式提问\n' +
              '2. 咨询人工客服';
   }
   ```

3. **Prompt 约束**：
   ```
   重要规则：
   - 如果检索结果与问题不相关，直接说"我不知道"
   - 不要编造文档中没有的信息
   - 不确定时，明确告知用户
   ```
```
