# 分层架构设计 - 为什么要分层？

## 核心问题
代码混乱、难以维护的根源是什么？

## 不分层的问题

### 1. 业务逻辑散落各处
```javascript
// routes/chat.js - 一个文件包揽一切
router.post('/chat', async (req, res) => {
  const { message } = req.body;

  // HTTP 处理
  if (!message) {
    return res.status(400).json({ error: '消息不能为空' });
  }

  // AI 调用
  const response = await callMiniMaxAPI(message);

  // 工具调用
  if (message.includes('天气')) {
    const weather = await fetchWeather();
    // ...
  }

  // RAG 检索
  const docs = await vectorSearch(message);

  // 数据库操作
  await saveToMongo(message, response);

  // 响应
  res.json({ response });
});
```

### 2. 问题汇总
| 问题 | 影响 |
|------|------|
| 业务逻辑散落 | 改一处影响全身 |
| 紧耦合 | 无法单独测试 |
| 职责不清 | 新人不知道在哪改 |
| 代码重复 | 相似逻辑复制多份 |

## 六层架构解决方案

```
┌─────────────────────────────────────────────────────────┐
│                       routes/                           │  HTTP 处理
│            接收请求、参数校验、调用下层、格式化响应           │
├─────────────────────────────────────────────────────────┤
│                      services/                           │  业务流程
│                  聊天编排、Agent 执行                       │
├─────────────────────────────────────────────────────────┤
│                       domain/                            │  核心业务
│              意图分类、工具选择、RAG 检索排序                 │
├─────────────────────────────────────────────────────────┤
│                        infra/                            │  基础设施
│             熔断、限流、缓存、指标采集、SSE                   │
├─────────────────────────────────────────────────────────┤
│                       common/                            │  通用基础
│                  错误定义、日志规范、通用工具                 │
├─────────────────────────────────────────────────────────┤
│                    application/                          │  应用编排
│                   跨模块协调、编排                          │
└─────────────────────────────────────────────────────────┘
```

## 各层职责详解

### Layer 1: routes/ - HTTP 处理层
```
职责：接收 HTTP 请求，返回 HTTP 响应
不应该有：业务逻辑、数据库操作、API 调用
```

```javascript
// routes/chat.js
router.post('/chat', async (req, res) => {
  try {
    // 1. 参数校验（这是 routes 该做的）
    const { message, sessionId } = req.body;
    if (!message) {
      return res.status(400).json({ error: '消息不能为空' });
    }

    // 2. 调用下层服务（不要在这里调用 AI！）
    const result = await chatService.sendMessage({ message, sessionId });

    // 3. 格式化响应
    res.json({ response: result.content });

  } catch (error) {
    // 4. 错误处理
    next(error);
  }
});
```

### Layer 2: services/ - 业务逻辑层
```
职责：业务流程编排、事务管理
不应该有：HTTP 处理、数据库连接
```

```javascript
// services/chatService.js
class ChatService {
  async sendMessage({ message, sessionId }) {
    // 1. 并行执行意图识别和 RAG 检索
    const [intent, context] = await Promise.all([
      this.intentClassifier.classify(message),
      this.ragService.retrieve(message)
    ]);

    // 2. 根据意图路由
    if (intent === 'tool') {
      return this.handleTool(message);
    } else if (intent === 'rag') {
      return this.handleRAG(message, context);
    }

    // 3. 调用 AI
    return this.callAI(message);
  }
}
```

### Layer 3: domain/ - 核心业务层
```
职责：纯业务逻辑、无副作用
不应该有：HTTP、数据库、第三方 API 调用
```

```javascript
// domain/rag/Reranker.js
```

### Layer 4: infra/ - 基础设施层
```
职责：技术基础设施、可复用组件
不应该有：业务逻辑
```

```javascript
// infra/circuitBreaker/CircuitBreaker.js
class CircuitBreaker {
  async execute(fn) {
    if (this.state === 'OPEN') {
      throw new CircuitOpenError();
    }

    try {
      return await fn();
    } catch (error) {
      this.recordFailure();
      throw error;
    }
  }
}
```

### Layer 5: common/ - 通用基础层
```
职责：错误定义、日志规范、通用工具
不应该有：业务逻辑
```

```javascript
// common/errors/AppError.js
class AppError extends Error {
  constructor(code, message, statusCode = 500) {
    super(message);
    this.code = code;
    this.statusCode = statusCode;
  }
}

class ValidationError extends AppError {
  constructor(message) {
    super('VALIDATION_ERROR', message, 400);
  }
}
```

### Layer 6: application/ - 应用编排层
```
职责：跨模块协调、复杂流程编排
```

```javascript
// application/ChatOrchestrator.js
class ChatOrchestrator {
  async process(message, sessionId) {
    // 1. 加载会话记忆
    const memory = await this.memoryService.load(sessionId);

    // 2. 并行执行多个服务
    const [intent, context] = await Promise.all([
      this.intentClassifier.classify(message),
      this.ragService.retrieve(message),
      this.memoryService.getRecentMessages(sessionId)
    ]);

    // 3. Agent 执行
    const response = await this.agentEngine.run({
      message,
      intent,
      context,
      memory
    });

    // 4. 保存记忆
    await this.memoryService.save(sessionId, message, response);

    return response;
  }
}
```

## 分层的好处

| 好处 | 说明 |
|------|------|
| 关注点分离 | 每层只关心自己的职责 |
| 易于测试 | 可以单独测试每层（mock 下层） |
| 可复用 | infra 和 common 可跨项目复用 |
| 并行开发 | 不同层分配给不同人 |
| 易于维护 | 修改某层不影响其他层 |

## 依赖规则

```
          ┌─────────────────────┐
          │    application/     │  ← 高层
          └──────────┬──────────┘
                     ↓
          ┌─────────────────────┐
          │     services/       │
          └──────────┬──────────┘
                     ↓
          ┌─────────────────────┐
          │      domain/        │
          └──────────┬──────────┘
                     ↓
          ┌─────────────────────┐
          │       infra/        │  ← 底层
          └─────────────────────┘
```

**规则**：上层调用下层，下层不调用上层

## 新手常见问题

Q: 如何选择放在哪一层？
A: HTTP 处理放 routes，业务逻辑放 services，核心算法放 domain，技术实现放 infra

Q: domain 和 services 有什么区别？
A: domain 是纯业务逻辑（无依赖），services 调用 domain 实现业务流程

Q: 小项目也需要分层吗？
A: 建议至少分成 routes/services 两层，避免业务逻辑散落

Q: 如何避免循环依赖？
A: 上层调用下层，如果 A 和 B 互相调用，说明它们应该在同一层
