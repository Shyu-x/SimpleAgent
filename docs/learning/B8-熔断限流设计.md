# 熔断限流设计 - 保护系统稳定性

## 核心问题
如何防止系统被突发流量击垮？如何避免级联故障？

## 不用熔断限流的后果

### 1. 雪崩效应
```
正常情况：
用户请求 → API → 数据库（响应正常）

异常情况：
用户请求 → API → 数据库（变慢）
用户请求 → API → 数据库（超时）
用户请求 → API → 数据库（崩溃）
         ↓
   更多请求堆积
         ↓
   API 也崩溃
```

### 2. 资源耗尽
- 线程池耗尽
- 连接池耗尽
- 内存溢出

### 3. 级联故障
```
服务A 调用 服务B
服务B 调用 服务C

C 挂了 → B 等待超时 → B 也挂了 → A 也挂了
```

## 熔断器模式

### 核心思想
"快速失败" 而不是 "一直等待"

### 三种状态
```
        ┌─────────────────────────────────────┐
        │                                     │
        ↓                                     │
    ┌───────┐    失败超阈值    ┌───────┐    探测成功    ┌────────┐
    │ CLOSED │ ──────────────→ │ OPEN  │ ─────────────→ │HALF-OPEN│
    │ 正常   │                │ 熔断  │               │  半开  │
    └───────┘ ←────────────── └───────┘ ←─────────────┘────────┘
     成功                熔断超时(30s)       失败
```

| 状态 | 行为 | 说明 |
|------|------|------|
| **CLOSED** | 正常请求通过 | 记录失败次数 |
| **OPEN** | 直接拒绝 | 快速失败，保护下游 |
| **HALF-OPEN** | 允许探测请求 | 测试下游是否恢复 |

### 熔断条件
- **打开条件**：连续失败超过阈值（如 5 次）
- **关闭条件**：熔断超时后（如 30 秒），进入半开状态
- **彻底关闭**：半开状态下探测成功

## 项目中的熔断器实现

### 文件位置
`backend/src/infra/circuitBreaker/`

### 核心代码
```javascript
// CircuitBreaker.js
class CircuitBreaker {
  constructor(options = {}) {
    this.failureThreshold = options.failureThreshold || 5;  // 失败阈值
    this.resetTimeout = options.resetTimeout || 30000;       // 重置超时
    this.state = 'CLOSED';
    this.failureCount = 0;
  }

  async execute(fn) {
    // OPEN 状态：直接拒绝
    if (this.state === 'OPEN') {
      throw new CircuitOpenError('Circuit is OPEN');
    }

    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }

  onSuccess() {
    this.failureCount = 0;
    if (this.state === 'HALF-OPEN') {
      this.state = 'CLOSED';  // 恢复正常
    }
  }

  onFailure() {
    this.failureCount++;
    if (this.failureCount >= this.failureThreshold) {
      this.state = 'OPEN';  // 打开熔断器
      setTimeout(() => {
        this.state = 'HALF-OPEN';  // 进入半开状态
      }, this.resetTimeout);
    }
  }
}
```

### 使用示例
```javascript
const breaker = new CircuitBreaker({
  failureThreshold: 5,
  resetTimeout: 30000
});

// 在服务中使用
class MiniMaxRouter {
  async callAPI(messages) {
    return breaker.execute(() => this.sendToMiniMax(messages));
  }
}
```

## 限流策略

### 1. 固定窗口限流
```
时间窗口：1 分钟
限制：100 请求

问题：窗口边界可能出现突发
|-------100------|-------100------|
0                1                2 分钟
         ↑ 边界突发：200 请求
```

### 2. 滑动窗口限流
```
更平滑，但实现复杂
```

### 3. 令牌桶算法
```javascript
class TokenBucket {
  constructor(rate, capacity) {
    this.rate = rate;        // 每秒补充的令牌数
    this.capacity = capacity; // 桶的容量
    this.tokens = capacity;
  }

  tryConsume() {
    if (this.tokens >= 1) {
      this.tokens--;
      return true;  // 通过
    }
    return false;  // 限流
  }

  // 定期补充令牌
  refill() {
    this.tokens = Math.min(this.capacity, this.tokens + this.rate);
  }
}
```

### 4. 队列限流（项目中使用）
```javascript
// backend/src/infra/rateLimiter/QueueRateLimiter.js
class QueueRateLimiter {
  constructor(options) {
    this.maxConcurrent = options.maxConcurrent || 10;  // 最大并发
    this.maxQueue = options.maxQueue || 100;           // 队列长度
    this.queue = [];
    this.running = 0;
  }

  async acquire() {
    // 如果正在运行的已达上限，加入队列
    if (this.running >= this.maxConcurrent) {
      return new Promise((resolve, reject) => {
        const timeout = setTimeout(() => {
          reject(new Error('Queue timeout'));
        }, 30000);

        this.queue.push({ resolve, reject, timeout });
      });
    }

    // 直接运行
    this.running++;
    return true;
  }

  release() {
    this.running--;
    // 取出队列中的下一个
    if (this.queue.length > 0) {
      const next = this.queue.shift();
      clearTimeout(next.timeout);
      next.resolve();
    }
  }
}
```

## 熔断 vs 限流

| 维度 | 熔断器 | 限流器 |
|------|--------|--------|
| **触发条件** | 下游故障 | 流量过大 |
| **目的** | 保护系统免受故障影响 | 保护系统免受超载影响 |
| **行为** | 快速失败 | 排队或拒绝 |
| **应用层级** | 服务调用级别 | 整体入口级别 |
| **恢复方式** | 自动探测恢复 | 流量下降后自动恢复 |

## 实际应用场景

### 场景 1：外部 API 熔断
```javascript
// MiniMax API 熔断保护
const miniMaxBreaker = new CircuitBreaker({
  failureThreshold: 3,    // 3 次失败
  resetTimeout: 60000    // 1 分钟后重试
});

async function callMiniMax(messages) {
  return miniMaxBreaker.execute(() =>
    fetch('https://api.minimaxi.com', messages)
  );
}
```

### 场景 2：并发限流
```javascript
// 聊天 API 限流
const chatLimiter = new QueueRateLimiter({
  maxConcurrent: 50,
  maxQueue: 200
});

router.post('/chat', async (req, res) => {
  try {
    await chatLimiter.acquire();
    // 处理请求...
  } finally {
    chatLimiter.release();
  }
});
```

## 新手常见问题

Q: 熔断和限流有什么区别？
A: 熔断是故障后的保护（下游已经出问题了），限流是预防性的（防止流量过大）

Q: 熔断器一直打开怎么办？
A: 检查下游服务是否真的挂了，可能是配置阈值太低

Q: 限流导致请求失败怎么办？
A: 可以让客户端重试（带退避），或返回 429 Too Many Requests

Q: 为什么不直接限制所有请求？
A: 限流会丢弃请求，熔断是快速失败保护，两者配合使用
