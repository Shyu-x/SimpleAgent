## 1. 行业最佳实践对比

| 维度 | Git Flow | Trunk-Based Development | 适合本项目 |
|------|----------|--------------------------|-----------|
| **分支结构** | master/develop/feature/release/hotfix (5类) | master + 短期 feature | **简化版 Trunk** |
| **分支数量** | 5+ 常驻分支 | 1-2 常驻分支 | 3 分支 |
| **复杂度** | 高 (需维护多个长生命分支) | 低 (频繁集成到 master) | 中低 |
| **团队适配** | 10+ 人大型团队 | 1-10 人小团队 | **1-2 人 (完美)** |
| **发布周期** | 2-4 周 | 1-7 天 | 每周 (完美) |
| **CI/CD 要求** | 复杂 (需多分支并行测试) | 简单 (统一 master) | 简单 |
| **回滚难度** | 需合并反向修改 | 直接 revert 或 forward-fix | 简单 |
| **学习成本** | 高 | 低 | 低 |
| **冲突风险** | 中 (长期分支可能) | 低 (频繁集成) | 低 |

**结论**: 对于 1-2 人团队 + 每周发布节奏，**Trunk-Based + Hotfix 模式**是最佳选择。

## 2. Feature Flag vs Feature Branch

| 维度 | Feature Branch | Feature Flag |
|------|---------------|---------------|
| **定义** | 代码级别的隔离 | 运行时开关控制 |
| **适用场景** | 破坏性改动、大重构、长时间开发 | 渐进式发布、A/B 测试、灰度 |
| **合并风险** | 大改动的长时间分支有冲突风险 | 无 (代码始终在 master) |
| **测试** | 独立测试 | 需环境变量/配置管理 |
| **项目适配** | 本项目短期迭代无需复杂管理 | 本项目不需要 (架构已稳定) |

**结论**: 本项目采用 **Feature Branch 模式**，feature 分支生命周期控制在 1-2 天内，无需 Feature Flag。

## 3. 推荐分支模型

### 3.1 分支架构

```
                    ┌─────────────┐
                    │   master    │ ← 稳定发布分支，保护规则
                    │  (受保护)   │   tag: v2.5.0
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ feature/ │ │ feature/ │ │  fix/    │
        │  agent   │ │   rag    │ │   ui     │
        │  engine  │ │  service │ │  bug     │
        └─────┬────┘ └─────┬────┘ └─────┬────┘
              │            │            │
              └────────────┴────────────┘
                           │
                           ▼
                    ┌─────────────┐
                    │  merge MR   │ ← Squash Merge 到 master
                    │   (CI 通过) │
                    └─────────────┘
```

### 3.2 分支类型定义

| 分支类型 | 命名规则 | 生命周期 | 合并目标 | 说明 |
|----------|---------|----------|---------|------|
| `master` | 固定 | 长期 | - | 稳定代码，始终可发布 |
| `feature/` | `feature/{type}-{description}` | ≤ 3 天 | master | 新功能开发 |
| `fix/` | `fix/{type}-{description}` | ≤ 1 天 | master | 常规修复 |
| `hotfix/` | `hotfix/{description}` | ≤ 4 小时 | master | 紧急修复，直接合并 |

## 5. PR/MR 流程

### 5.1 标准流程

```
1. 创建分支
   git checkout -b feature/agent-retry

2. 开发 & 提交 (遵循 commitlint)
   git commit -m "feat(agent): add exponential backoff retry"

3. 推送分支
   git push -u origin feature/agent-retry

4. 创建 MR (GitLab/GitHub)
   - 填写 MR 模板
   - 关联相关 issue

5. CI 自动检查
   - ✅ lint (commitlint + eslint)
   - ✅ test (Jest/Vitest)
   - ✅ build (Docker build)

6. 代码审查
   - 至少 1 人 approval
   - 建议审查清单：
     □ 功能符合需求
     □ 无性能退化
     □ 测试覆盖
     □ 无敏感信息泄露

7. Squash Merge 到 master
   - 删除 source branch
   - 自动触发 deploy-staging

8. 删除本地分支
   git branch -d feature/agent-retry
```

### 5.2 MR 模板

```markdown
## 概述
<!-- 简要描述改动的目的 -->

## 改动范围
<!-- 列出改动的文件和组件 -->

## 测试验证
- [ ] 本地测试通过
- [ ] E2E 测试通过
- [ ] 边界情况处理

## 相关链接
<!-- 关联的 issue 或文档 -->

## 截图 (如适用)
<!-- UI 改动需附截图 -->
```

## 6. CI/CD 集成

### 6.1 增强建议

```yaml
# 新增分支保护规则 Job
branch-protection:
  stage: .pre
  script:
    - |
      # Master 必须通过所有检查才能合并
      if [ "$CI_COMMIT_BRANCH" == "master" ]; then
        echo "Master 分支需通过所有 CI 检查"
        exit 0
      fi
  rules:
    - if: $CI_COMMIT_BRANCH == "master"

# 新增 feature 分支快通道
lint:feature:
  stage: lint
  script:
    - npx eslint src/ --max-warnings=5  # Feature 分支容忍警告
  rules:
    - if: $CI_COMMIT_BRANCH =~ /^feature.*$/
```

### 6.2 自动化版本标签

```yaml
# 自动版本标签
version:tag:
  stage: deploy-production
  script:
    - |
      if [ "$CI_COMMIT_BRANCH" == "master" ]; then
        TAG="v$(date +%Y.%m.%d)-$(git rev-parse --short HEAD)"
        git tag $TAG
        git push origin $TAG
      fi
  only:
    - master
```

## 7. Git Hooks 增强

### 7.1 现有 Hooks

| Hook | 触发时机 | 功能 | 状态 |
|------|---------|------|------|
| `pre-commit` | 提交前 | 敏感信息检测 + ESLint | ✅ 已配置 |
| `commit-msg` | 提交信息 | commitlint 验证 | ✅ 已配置 |

### 7.2 增强建议

```bash
# backend/.husky/pre-push
#!/bin/sh
#
# Pre-Push Hook - 推送前增量检查
#

echo "🔍 Pre-Push 检查..."

# 检查分支命名
BRANCH=$(git symbolic-ref --short HEAD)
if ! echo "$BRANCH" | grep -qE "^(feature|fix|hotfix|chore|refactor)/"; then
  if [ "$BRANCH" != "master" ]; then
    echo "✖ 分支命名不符合规范: $BRANCH"
    echo "  期望: feature/*, fix/*, hotfix/*, chore/*, refactor/*"
    exit 1
  fi
fi

# 禁止强制推送到 master
if [ "$BRANCH" == "master" ]; then
  if git log origin/master..HEAD --oneline | grep -q .; then
    echo "✖ 禁止直接推送到 master，请通过 MR 合并"
    exit 1
  fi
fi

echo "✓ Pre-Push 检查通过"
```

## 8. 分支操作 SOP

### 8.1 开始新功能

```bash
# 1. 确保 master 最新
git checkout master
git pull origin master

# 2. 创建 feature 分支
git checkout -b feature/ui-dark-mode

# 3. 开发并提交 (遵循 commitlint)
git commit -m "feat(ui): add dark mode support"

# 4. 推送并创建 MR
git push -u origin feature/ui-dark-mode
# 然后在 GitLab/GitHub 界面创建 MR
```

### 8.2 Hotfix 紧急修复

```bash
# 1. 从 master 创建 hotfix 分支
git checkout master
git pull origin master
git checkout -b hotfix/memory-leak-fix

# 2. 修复并提交
git commit -m "hotfix: prevent memory leak in agent pool"

# 3. 直接合并到 master (绕过 MR 审批，但需 CI 通过)
git checkout master
git merge --no-ff hotfix/memory-leak-fix
git push origin master

# 4. 删除 hotfix 分支
git branch -d hotfix/memory-leak-fix
```

## 10. 总结与建议

### 10.1 推荐方案总结

| 项目 | 建议值 |
|------|-------|
| 分支模型 | Trunk-Based + Hotfix |
| 常驻分支 | master (1个) |
| 分支类型 | feature/ fix/ hotfix/ chore/ refactor |
| 合并方式 | Squash Merge (保持线性历史) |
| MR 要求 | 至少 1 人 approval |
| CI 门禁 | 全量检查必须通过 |
| 分支生命周期 | feature ≤ 3天, fix ≤ 1天, hotfix ≤ 4小时 |

### 10.2 立即可执行的动作

1. **创建分支保护规则** (GitLab)
   - Master 分支禁止直接推送
   - 必须通过 MR 合并
   - 至少 1 人 approval

2. **增强 Git Hooks**
   - 添加 `pre-push` 检查分支命名
   - 完善 `post-checkout` 提示

3. **更新 CI 配置**
   - 添加分支特定的测试策略
   - 配置自动版本标签

4. **文档化**
   - 将本规范添加到 `CLAUDE.md`
   - 创建 `.github/PULL_REQUEST_TEMPLATE.md`

### 10.3 迁移路径

```
当前状态: 只有 master 分支
        ↓
Phase 1: 启用分支保护 + MR 流程 (1天)
        ↓
Phase 2: 培训团队使用 feature 分支 (1天)
        ↓
Phase 3: 增强 CI/CD + Hooks (2天)
        ↓
最终状态: 完整的分支策略体系
```
